# MASAR Care — Independent Source Audit
**Based on:** user-supplied `masar-care.zip` (V1.5.1)  
**Status:** source review only; no migrations executed, no database connected, no application source modified.  
**Decision:** Shared Supabase project (Option B) approved by project owner.  
**Scope inspected:** React/TypeScript UI and context, scheduling/refill engines, in-memory adapter, SQL 0001/0002, documented tests, package setup.

## Executive decision
**Retain and improve the existing project. Do not run either SQL migration as currently written.**

The archive contains 21 proposed tables, 40 RLS policies, six SQL helper/RPC functions, 29 source files under `src`, and three test scripts. The prototype separates dispensing from confirmed adherence and has useful regimen-versioning and refill logic. However, security-critical invitation behavior, relational integrity, the Supabase data adapter boundary, and real-time dates need correction. Reported application tests are not equivalent to execution of the actual SQL policies.

## Confirmed findings from source inspection

| ID | Severity | Finding and evidence | Required change / acceptance criteria |
|---|---|---|---|
| C1 | **Critical** | Failed redemption logic performs UPDATE/INSERT then `RAISE EXCEPTION` in `supabase/migrations/0002_stage2a_rls_and_security.sql:630–673`. The exception rolls back those writes in the same transaction, so lockout and failure tracking do **not** persist as intended. | Return a structured failure response or persist failure state in an independently committed trusted boundary. Real DB tests must prove counters/lockouts persist after bad PIN/OTP, expiry, revoked invite, and replay. |
| C2 | **Critical** | `redeem_patient_apk_invitation` accepts `p_client_ip_hash` as caller-provided text (`0002:591–597`) and uses it as the IP limiter key (`0002:612–621`); callers can supply arbitrary values. | Derive abuse signals from a trusted proxy/backend, not a client argument; combine per-token, account, phone, device and server-side rate limits. |
| C3 | **Critical** | `sms_otp_hash` is defined (`0001:505–506`) and required at redemption (`0002:653–659`), but neither migration contains an OTP generation/issuance step. The ZIP contains no backend SMS service or Edge Function. Thus the described redemption flow cannot succeed in this state. | Build and test trusted OTP issuance, verified-phone ownership, expiry, resend policy, recovery path and invitation redemption; do not bypass OTP verification. |
| C4 | **Critical** | Tables such as `dose_events` (`0001:275–297`), `dispensing_events` (`0001:306–336`), `scheduled_doses` (`0001:245–264`) and `refill_assessments` (`0001:349–372`) independently FK `patient_id` and `medication_plan_id` to records in the same **pharmacy**, without constraining that the plan belongs to that **patient**. Database may accept patient A plus plan B from patient B in the same pharmacy. | Add composite unique key `(id,patient_id,pharmacy_id)` to medication plans and composite FKs for referencing tables, plus consistency for `scheduled_dose_id`, regimen version, refill last dispensing event and related references. Include negative SQL inserts that must fail. |
| H1 | **High** | Operational date is fixed: `src/i18n/translations.ts:19` sets `APP_REFERENCE_DATE = '2026-11-12'`; dashboard/context, dispensing, follow-ups, archiving and dose timeline use it. | Keep frozen clock only in demo/test fixtures. For real use, inject a clock with Baghdad local current date, refresh across midnight and test date transitions. |
| H2 | **High** | `ICrmDataAdapter` uses synchronous return values (`src/services/crmRepository.ts:94–134`) and `CrmContext` is typed to `InMemoryCrmAdapter` (`src/context/CrmContext.tsx:116–122`). Supabase operations are asynchronous and can fail. A drop-in adapter is not possible as currently claimed. | Design async repository contract with `Promise`, loading/error states, optimistic updates where safe, server-generated IDs, retries/idempotency, and session-aware cache invalidation before implementation. |
| H3 | **High** | `issue_patient_apk_invitation` uses PostgreSQL `random()` to create six-digit handover PIN (`0002:550–554`), not a cryptographically secure generator. | Generate PIN through a cryptographic source; hash with appropriate work factor; never log plaintext PIN or token. |
| H4 | **High** | `redeem_patient_apk_invitation` requires `auth.uid()` before account linking (`0002:608–609,675–688`), yet the product disallows independent patient self-registration. No controlled first-login/identity provisioning flow is implemented. | Define a trusted bootstrap flow (limited-purpose verified session or server-mediated activation), idempotent auth-user creation, atomic linking or compensating recovery, and anti-account-takeover checks. |
| H5 | **High** | `patients.phone` is unique per pharmacy (`0001:76`). This disallows two patients sharing a caregiver/family phone even though such sharing may be legitimate. | Treat normalized phone as a contact method, not a unique person identifier. Keep duplicate warnings; separately model verified account phone and account ownership. |
| H6 | **High** | Composite FKs on `refill_assessments.last_dispensing_event_id` (`0001:371–372`) and `follow_up_tasks.related_medication_plan_id` (`0001:425–426`) have `ON DELETE SET NULL` covering **both** FK columns, including `pharmacy_id NOT NULL`. This cannot safely perform the intended deletion behavior. | Use column-list SET NULL only on the optional FK column if supported and appropriate; otherwise `RESTRICT` / explicit historical retention. Verify actual delete behavior. |
| H7 | **High** | `simulateSupplyDepletionFromOccurrences` returns an arbitrary next-day fallback (`src/services/scheduleEngine.ts:516–526`) when no depletion occurs before the horizon. For finite courses or excess stock, this can label a fictional refill date. | Return a clear `no_depletion_within_plan` / `unable_to_estimate` status and null date when no future dose goes unfilled. Add finite-course, 10-year-bound and surplus-stock tests. |
| H8 | **High** | RPC issue method checks patient active but not whether already linked to `auth_user_id` (`0002:535–540`). Redemption can replace `patients.auth_user_id` (`0002:684–688`) without a separate account-recovery ceremony. | Distinguish initial activation from lost-device recovery and account replacement; require additional authorization and audit for the latter. |
| M1 | Medium | UI mock `QrPreview` draws a deterministic random-looking matrix, not an encoded, scannable QR (`src/components/ui/QrPreview.tsx`). | Keep clearly labeled DEMO until secure backend; use an actual QR encoder for real activation links after validation. |
| M2 | Medium | `src/types/supabaseSchemaSpec.ts` contains an in-memory `Stage2SecurityPolicyEvaluator` used by tests, not an execution of PostgreSQL RLS. | Add SQL-level tests under real distinct Auth sessions and database roles; deny unauthorized reads, writes, updates, link reassignment and RPC calls. |
| M3 | Medium | `package.json` lacks test scripts and an exported lockfile; no `package-lock.json`/`pnpm-lock.yaml` is present in the ZIP. Reported test scripts cannot be reproduced directly by `npm test` with fixed dependencies. | Add `test`, `test:unit`, `test:e2e`, `typecheck`, `lint` scripts, pin dependencies, commit lockfile, configure CI, and add Playwright browser tests. |
| M4 | Medium | Large UI files, e.g. `MedicationWizardModal.tsx` (~65KB) and `PatientDetailView.tsx` (~62KB), plus one global `CrmContext`, increase regression risk. | Split by feature into smaller forms, views, validation modules, hooks and queries while preserving current workflows. Add routing/deep-link support. |
| M5 | Medium | Current schema models one `pharmacy_staff` row per Auth user (`0001:55–57`) and one `patients.auth_user_id` per patient globally. Multi-branch staff/patient use would require a future membership/link structure. | Document explicitly whether V2 supports single-pharmacy membership, and design a migration-safe path to multi-pharmacy accounts. |
| M6 | Medium | Patient RLS allows patient `UPDATE dose_events` for own record (`0002:372–387`) but lacks server-enforced state transitions and audit provenance for changes to confirmations. | Separate append-only patient dose actions from mutable daily summary; enforce ownership of scheduled occurrence, idempotency, sensible times, amendment trail and server-set timestamps. |
| M7 | Medium | SQL helper and invitation RPCs are `SECURITY DEFINER` in the exposed `public` schema (`0002:11–76,507–718`). | Review `EXECUTE` grants, function ownership, safe search_path, RLS-bypass assumptions, and moved private helper functions; test least-privilege access on actual Supabase dev DB. |
| M8 | Medium | The current handoff still says Option B awaits approval (`docs/MASAR_CARE_HANDOFF.md`), which is now outdated. | Update architecture decision record: Option B approved; migration execution still not approved. |

### Additional design checks
- Verify `regimen_versions` historical `effective_to` update permissions against the promise of immutability; add effective-date overlap constraints, controlled closure API and audit. (`0001:196–218`; `0002:166,313–325`.)
- Constrain pause intervals to avoid overlapping windows and invalid resumes; preserve clinical history.
- Validate scheduled dose ↔ dose event linkage and cross-patient consistency; a simple FK by scheduled dose UUID alone is not enough.
- Ensure trusted backend, not patients' devices, supplies authoritative timestamps and identity fields; design deduplicated offline dose events.
- Add owner/staff bootstrap procedure and a private platform-admin authorization model; there is no backend administration implementation in the archive.
- Review clinical unit conversion between doses and dispensing units (e.g. mg vs tablets, IU vs mL, inhalers/puffs) before allowing auto-refill forecasts.
- Retain physical-deletion restrictions / archival strategy for clinical histories. Some current FKs use ON DELETE CASCADE.
